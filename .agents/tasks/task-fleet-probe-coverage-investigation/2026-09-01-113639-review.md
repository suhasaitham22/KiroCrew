# Review of the fleet_probe.py coverage investigation (issue #7597)

The deliverable is a diagnostic report, `INVESTIGATION.md`, that argues #7597's 14.8%
`fleet_probe.py` reading is a CI coverage-arm truncation artifact (the #7516 / PR #7517
class) rather than an undertested file, and therefore declines to add tests or a coverage
baseline entry. The review below judges whether the report's evidence actually supports
that disposition and whether any cited fact is wrong or overstated. I re-read the report
from disk and cross-checked every file:line citation against the working tree.

The disposition is sound and the evidence is strong: the tests the gate asks for demonstrably
exist and drive the function bodies, a sibling script through the identical load path is
unbaselined and passing, and the truncation mechanism is self-documented in `ci.yml`. The
citations are accurate to the line in almost every case, with two off-by-a-few line-number
drifts that don't affect any claim. The second-suggestion assessment (Coverage Gate already
triggers on push to main; the real gap is concurrency-driven periodic verdicts) is correct
and, if anything, understated as a caveat rather than overstated.

Watch for: one factual soft spot worth tightening before this goes back on the issue — the
report treats "a shard whose tests all ran shows only import-time lines" as the mechanism, but
the shard-upload step (`ci.yml:706`) actually fails the job with `exit 1` if a shard produced
no `.coverage`, so the truncation story depends specifically on a shard dying *before* that
step at the wall, not on a shard silently uploading empty data (confirmed). The report's chain
is correct but skates over this step; a reader who checks `ci.yml` will notice the guard and
may think the report missed it. (possible)

**Verdict**: APPROVED

## High-level view

The central claim — file is covered, reading is a truncation artifact — rests on three
independent legs, and all three hold up against the tree. `TestFleetProbe` exists at the cited
line with the cited loader and 20 test methods (the report says 20; the issue's "roughly 25" is
the looser number), the nine named tests it leans on all exist, and they invoke `mod.main([...])`
so they exercise the function bodies whose absence from the reading is the whole anomaly. The
`git log` and baseline-absence facts are correct.

The decisive control case is real: `credit_spend.py` sits in the same directory, is loaded by
the same `load_skill_script` in the same test file (`TestCreditSpend` at :453), is absent from
`backend.txt`, and passes the gate — so the importlib load path does not defeat coverage
attribution. This is the strongest single leg of the argument.

The truncation mechanism is genuinely self-documented in `ci.yml`: coverage only on 3.12 shards
(`:692`), four-way split, and a shard-wall comment (`:581-583`) that spells out the exact
failure. The combine job (`:973`) downloads `coverage-shard-*` with `merge-multiple: true`
(`:1004-1005`) and has no all-shards-present assertion, so it succeeds on partial data. The one
nuance the report underplays is the per-shard upload guard at `ci.yml:706` that hard-fails a
shard producing no coverage — consistent with the report's "shard dies at the wall" framing but
not called out.

The second-suggestion correction is accurate and precise: the workflow's `on:` block triggers on
both push-to-main and pull_request (`:3-6`), so "effectively PR-only" is imprecise; the real gap
is the `concurrency` block (`:11-19`) yielding periodic rather than per-commit verdicts on main.
The report correctly scopes this as a separate CI-policy issue and does not let it contaminate the
diagnosis.

### The tests exist and drive the bodies — verified

Every citation in Evidence 1 checks out. `class TestFleetProbe:` is at
`test/test_pipeline_conductor_agent.py:179`; `_mod()` loads the real script via
`load_skill_script("fleet_probe", SKILL_DIR / "scripts" / "fleet_probe.py")` at `:181`;
`SKILL_DIR` is defined at `:26`. An `awk` count of `def test_` between lines 179 and 453
returns exactly 20, matching the report. All nine named tests exist at concrete lines
(`test_protocol_tag_fires_and_working_stays_quiet:219`, `test_missing_transcript_reports_gone:243`,
`test_fired_lines_carry_metadata_never_transcript_text:249`,
`test_typed_misconfiguration_is_malformed_config:353`,
`test_traversal_session_keys_are_malformed_config:360`,
`test_corrupt_handled_map_degrades_to_empty:371`, `test_symlink_out_of_the_store_reads_gone:400`,
`test_nonfinite_numeric_config_is_malformed:414`, `test_malformed_config_exits_2:425`).

The load-bearing detail behind the "34/229 is import-time-only" argument is that these tests
actually execute the function bodies — each drives `self._run(mod, cfg, capsys)`, which asserts
`mod.main(...)` and reads its stdout. So had the covering data landed in the combine, the function
bodies would be attributed, not just the imports and `def` headers. That makes the import-time-only
signature a real discriminator between "no tests" and "tests dropped", which is the pivot the
report's diagnosis turns on.

`git log -- src/kiro_crew/builtin_skills/pipeline-conductor/scripts/fleet_probe.py` returns a
single commit, `c0dca4a8b`, refuting the issue body's "No commit since has added tests for it" —
the tests arrived with the script.

### The control case is the strongest leg — verified

`TestCreditSpend` is at `:453` and loads `credit_spend.py` from the same
`SKILL_DIR / "scripts"` via the same helper. `grep` over
`.github/coverage-baselines/backend.txt` returns no match for either `credit_spend` or
`fleet_probe`. `load_skill_script` is at `test/skill_script_helpers.py:55` and uses
`spec_from_file_location`; `setup.cfg:366-368` carries `[coverage:paths] / source = / src/`.
The empirical control case makes the mechanism argument decisive: if the loader defeated
attribution, `credit_spend.py` and the other same-loader scripts would sit near 0% and red the
floor too, and they do not.

### Truncation mechanism — verified, with one unmentioned guard

The `ci.yml` chain is accurate. Coverage is gated to 3.12 via
`${{ matrix.python-version == '3.12' && '--cov=kiro_crew --cov=sage_lib' || '--no-cov' }}` at
`:692`; the shard-wall comment is verbatim at `:581-583` ("The slowest 3.12 shard runs
~29 minutes, so a 30-minute cap kills the job at the coverage step..."); `timeout-minutes: 40`
follows at `:584`, and the report correctly flags that the comment still says "30-minute" while
the cap was raised to 40, noting this widens the margin without changing the failure shape. The
`coverage-combine` job is at `:973`, downloads `pattern: coverage-shard-*` with
`merge-multiple: true` at `:1004-1005`, and runs `coverage combine` / `coverage xml -o coverage.xml`
/ `coverage report` at `:1012-1014`, with no assertion that all four shard artifacts are present.

The gap the report skates over: the per-shard "Stage shard coverage data" step at `ci.yml:705-708`
runs `coverage combine` then `test -f .coverage || { echo "::error::..."; exit 1; }` before
renaming to `.coverage.<group>`. A shard that runs to completion therefore cannot upload *empty*
coverage — it either uploads real data or the shard job itself reds. So the truncation the report
describes specifically requires the shard to be killed at the wall *before* reaching that step,
which is exactly the scenario the `:581-583` comment describes ("kills the job at the coverage
step"). The report's story is internally consistent, but it presents the combine job's missing
all-present assertion as the whole mechanism without acknowledging the upstream guard that forces
the failure to be a wall-death rather than a silent empty upload. Naming that guard would make the
diagnosis airtight against a reviewer who reads `ci.yml` top to bottom.

A related edge the report omits: `coverage combine` with *zero* data files exits non-zero ("No data
to combine"), so the partial-success path requires at least one surviving shard — the realistic
case (one of four lost), so the conclusion stands.

### Second suggestion — accurate, not overstated

The `on:` block at `ci.yml:3-6` fires on both `push: branches: [main]` and
`pull_request: branches: [main]`, so the report's correction of the issue's "effectively PR-only"
framing is factually right. The `concurrency` block at `:11-19` sets
`cancel-in-progress: ${{ github.event_name == 'pull_request' }}` and carries an in-file comment
explaining that main gets periodic rather than per-commit verdicts because GitHub evicts a pending
run when a newer one queues — the report's characterization matches the workflow's own comment
almost word for word. The report scopes this as a distinct CI-policy issue and explicitly notes it
would not have caught anything for #7597 (the file is covered), so the framing is not overstated.

### Disposition and constraints — verified

The two negative constraints hold: `git status` shows only the untracked `.agents/` directory (no
edits to the test file, `fleet_probe.py`, `ci.yml`, or `backend.txt`), and neither `fleet_probe` nor
`credit_spend` appears in `backend.txt`. The report states plainly that empirical coverage
measurement was blocked by INTEGRATIONS_ONLY and that the conclusion is static; given the control
case and the self-documented mechanism, that is a defensible basis for the disposition. The
recommendation — route to needs-investigation, decline tests and baseline, file the main-verdict
concern separately — follows from the evidence.
